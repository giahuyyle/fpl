FPL Authentication Handoff

Goal: Add first-party user authentication to the React SPA and FastAPI/PostgreSQL backend.

Current state and blocker

backend/app/db/schema.py currently declares class User(DeclarativeBase). This breaks module import with InvalidRequestError. It must be class User(Base), or Alembic and tests cannot see the table.

  • The current user fields are username, optional email, password hash, and season-specific favorite team.
  • backend/main.py allows credentialed CORS from http://localhost:5173, but origins should move to configuration and methods/headers should be restricted.
  • No auth routes, schemas, services, sessions, password utilities, migration, CSRF protection, or auth tests exist yet.
  • Do not edit an already-applied initial migration; create a new Alembic revision.

Recommended design

Use opaque, server-side sessions rather than JWTs for this first-party browser application.

  1. Login verifies an Argon2id password hash.
  2. Generate a random token with secrets.token_urlsafe(32).
  3. Return the raw token only in an HttpOnly cookie.
  4. Store only the token's SHA-256 hash in an auth_sessions table.
  5. Resolve the current user from an unexpired, unrevoked session on each request.
  6. Revoke on logout; revoke other sessions after password changes.

Cookie baseline: HttpOnly, Secure outside local development, SameSite=Lax, Path=/, explicit expiry. React requests must use credentials: "include". Never store auth tokens in local/session storage.

Target database shape

User

  • Inherit from Base.
  • Bound username/email lengths and make required fields non-null.
  • Add database-unique normalized username and email fields.
  • Store password_hash, never plaintext or reversible encryption.
  • Add is_active, email_verified_at, and timezone-aware created_at.
  • Consider a season-independent Club model for favorites; current Team rows belong to a season. Until then use nullable FK with ondelete="SET NULL".

AuthSession

  • token_hash: unique, non-null, 64-character SHA-256 hex digest.
  • user_id: FK to users with cascade delete.
  • created_at, expires_at, optional revoked_at; all timezone-aware.

Security requirements

  • Argon2id password hashing; unique salts are handled by the library.
  • For password-only auth: minimum 15 characters, permit at least 64, no arbitrary composition rules, and block common/compromised passwords.
  • Never strip or silently transform passwords. If Unicode normalization is adopted, apply it consistently before hashing and verification.
  • CORS is not CSRF protection. Require an X-CSRF-Token or equivalent custom-header defense plus trusted Origin checks for POST/PUT/PATCH/DELETE.
  • No state changes through GET.
  • Use generic login/recovery responses to reduce account enumeration.
  • Recovery tokens must be random, stored hashed, short-lived, single-use, and rate-limited.
  • Authorization must scope every user-owned query to the authenticated user; never trust a client-supplied user ID.
  • Use HTTPS in production; do not log passwords, raw sessions, reset tokens, or secrets.

Required tests

  • Normalization and concurrent database uniqueness.
  • Passwords never persist verbatim; correct/incorrect verification.
  • Generic login failures and inactive/unverified-user behavior.
  • Session token stored only as a hash; expiry, revocation, logout, and rotation.
  • Cookie flags and frontend credential inclusion.
  • Missing/invalid CSRF token and untrusted Origin rejection.
  • Rate limits and password-reset token expiry/single use.
  • IDOR checks: one user cannot read or mutate another user's resources.
  • Full Alembic history upgrades to head and downgrades cleanly. Update the current migration test so it no longer compares only the initial revision with final metadata.
  • Include PostgreSQL integration tests for PostgreSQL-specific uniqueness/index behavior; SQLite alone is insufficient for those cases.
